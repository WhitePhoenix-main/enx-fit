# Администрирование Enix Fit

Панель доступна по `/Admin` и через пункт «Администрирование» в меню приложения. Требуется роль уровня 8 или 9.

## Числовые роли

Роль хранится в поле `Role` (integer, NOT NULL) таблицы `AspNetUsers`. В коде это `ApplicationUser.Role` типа `UserRole` из `enx-fit/Security/UserRole.cs`.

| Число | Enum | Назначение |
| --- | --- | --- |
| 0 | `Guest` | Авторизованный гость, без доступа к личным разделам |
| 1 | `User` | Обычный пользователь; роль при регистрации, если в таблице уже есть пользователи |
| 3 | `Trainer` | Тренер |
| 5 | `Moderator` | Модератор |
| 8 | `Administrator` | Управление пользователями и тренировками |
| 9 | `SuperAdministrator` | Главный администратор, максимальные права |

Права иерархические: проверку уровня 3 проходят роли 3, 5, 8, 9. Роли тренера и модератора пока дают доступ к личным разделам; отдельные возможности для них можно включать проверками ниже. Роль 0 также требует входа; публичная страница не должна иметь такую проверку. База отклоняет значения, отсутствующие в enum. При добавлении новых значений обновите ограничение `CK_AspNetUsers_Role` в модели `IdentityContext` и создайте миграцию.

Роль выбирается в **Администрирование → Пользователи → Редактировать → Роль**. Нельзя менять свою роль, назначать уровень выше собственного или редактировать профиль пользователя с более высокой ролью.

Если таблица `AspNetUsers` пуста, первый успешно зарегистрированный аккаунт автоматически получает `Administrator` (уровень 8). Это действует для регистрации с паролем и через внешний провайдер. Проверка и создание аккаунта выполняются в одной транзакции с блокировкой в PostgreSQL, поэтому одновременные регистрации не создадут нескольких первых администраторов. Если пользователи уже есть, новые аккаунты получают уровень 1, даже если администраторов нет.

Для назначения максимальной роли напрямую в PostgreSQL после применения миграции:

```sql
UPDATE "AspNetUsers"
SET "Role" = 9
WHERE "NormalizedEmail" = UPPER('your-email@example.com')
RETURNING "Id", "Email", "Role";
```

Проверка доступа читает роль из БД на каждом авторизованном запросе. Обновление через SQL действует со следующего запроса без выхода из аккаунта. Источник прав — поле `Role`; записи в `AspNetUserClaims` и старые связи `AspNetUserRoles` не повышают числовой уровень. Строковая роль `Administrator` формируется для совместимости существующих представлений при уровне от 8.

## Доступ к страницам через enum

Добавьте атрибут **к классу PageModel** в файле `*.cshtml.cs`:

```csharp
using enx_fit.Security;
using Microsoft.AspNetCore.Mvc.RazorPages;

[MinimumRole(UserRole.Trainer)]
public class ReportsModel : PageModel
{
    public void OnGet() { }
}
```

Для страницы только главного администратора используйте `[MinimumRole(UserRole.SuperAdministrator)]`. Проверка защищает всю страницу, включая POST. Атрибут не предназначен для отдельных `OnGet`/`OnPost`-обработчиков.

Для отдельного действия внутри обработчика:

```csharp
if (!User.HasMinimumRole(UserRole.Moderator))
    return Forbid();
```

Для отображения кнопки в `.cshtml` (пространство имён уже подключено в `Pages/_ViewImports.cshtml`):

```cshtml
@if (User.HasMinimumRole(UserRole.Administrator))
{
    <a asp-page="/Admin/Users/Index">Пользователи</a>
}
```

В обработчике действия нужна такая же серверная проверка. Скрытие кнопки само по себе доступ не ограничивает.

Доступ задаётся вручную атрибутом `[MinimumRole(...)]` на классе PageModel каждой страницы. Страницы `/Admin` и изменение справочника упражнений требуют уровня 8; `/Dashboard`, `/Workouts`, `/Body`, `/Analytics` и просмотр упражнений — уровня 1. `Security/RoleAuthorizationExtensions.cs` регистрирует политики ролей, но не содержит списка страниц и правил папок.

При добавлении новой защищённой страницы обязательно укажите атрибут на её PageModel: расположение в папке `/Admin` само по себе доступ не ограничивает. Для страницы без PageModel создайте класс модели и подключите его через `@model`, как у `/Dashboard`. Публичным страницам атрибут ограничения не нужен.

## Возможности

- Обзор: показатели из базы, активность за 7/30/90 дней, последние тренировки и популярные упражнения.
- Пользователи: поиск по имени и email, фильтр ролей, страницы по 12 записей, создание аккаунта, редактирование имени, email, телефона и роли.
- Профиль: переход к тренировкам и замерам пользователя; создание тренировки с уже выбранным владельцем.
- Тренировки: создание, редактирование, удаление с отдельной страницей подтверждения, добавление упражнений и подходов.
- Упражнения и замеры: существующие операции приложения в едином оформлении панели.

Изменение email и телефона сбрасывает соответствующий признак подтверждения. Изменения профиля и роли сохраняются в транзакции. Вход выполняется по email независимо от имени пользователя.

## Запуск

После обновления кода перезапустите приложение обычным способом или выполните:

```powershell
dotnet run --project enx-fit/enx-fit.csproj
```

При использовании профиля `http`: `http://localhost:5142/Admin`.

Миграция `AddUserRoleLevel` применяется автоматически при запуске приложения: добавляет поле `Role`, назначает обычным аккаунтам уровень 1, а существующим участникам Identity-роли `Administrator` — уровень 9. Пользователи и их данные сохраняются.

На пустой базе достаточно зарегистрировать первый аккаунт: он получит уровень 8 автоматически. Для назначения уровня 9 используйте SQL выше. Если в таблице уже есть пользователи, автоматическое назначение администратора не выполняется.

При запуске приложение также удаляет повреждённые записи Identity с пустым `ClaimType`: такие строки не позволяют ASP.NET Identity восстановить claims авторизованного пользователя.

## Оформление

`Pages/Shared/_AdminLayout.cshtml`, `wwwroot/css/admin.css` и `wwwroot/js/admin*.js` написаны для панели с нуля. WiseOwl служит визуальным образцом: тёмное меню, светлые карточки, синие акценты и шрифт Montserrat. Используются локальные файлы шрифта из шаблона и имеющаяся Chart.js. CSS и JavaScript самого WiseOwl, Bootstrap и стили публичного сайта в панель не подключаются.

Для администраторов страницы `/Workouts`, `/Exercises` и `/Body` получают новый layout. Для остальных пользователей сохраняется прежний layout. Подписи этих разделов переведены на русский.

## Проверки

Проверки автоматического назначения первого администратора (изолированная SQLite-база, без подключения к рабочей базе):

```powershell
dotnet run --project tests/RegistrationSmoke/RegistrationSmoke.csproj -p:UseAppHost=false
```

Проверяются регистрация с паролем и внешним аккаунтом, уровень 8 для первого пользователя, уровень 1 для последующих, откат неудачной регистрации и отсутствие повышения прав при наличии пользователей без администратора. Конкурентная блокировка PostgreSQL этими SQLite-проверками не проверяется.

```powershell
dotnet run --project tests/AdminSmoke/AdminSmoke.csproj -p:OutputPath=bin/Smoke/ -p:UseAppHost=false
```

Тестовый проект запускает настоящие скомпилированные Razor Pages с Identity и SQLite-базами в памяти на порту 5187. Рабочая PostgreSQL-база не используется. Проверяются иерархия enum, атрибуты страниц, смена роли через SQL при действующей сессии, старые claims, защита от повышения прав, регистрация с уровнем 1, CSRF, фильтры, страницы пользователей, создание и изменение профилей, вход после переименования, создание тренировок, подходы и изоляция владельцев.

Для ручной проверки можно добавить `-- --serve`; для другого порта — `-- --port 5190 --serve`. Тестовый стенд выведет данные входа в консоль и будет работать до Ctrl+C. Этот проект предназначен только для локального тестирования; данные существуют до завершения процесса. SQL-запросы проверяются на SQLite; основной провайдер приложения — PostgreSQL.
